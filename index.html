為什麼需要多個 Agent？

!
Context 爆炸 — 所有工具、記憶、指令塞同一個 window，token 成本暴漲
!
角色混亂 — 同時當助理、工程師、分析師，品質直線下降
!
工具權限 — 不同任務需要不同權限，全開 = 風險
!
無法平行 — 一個 agent 同一時間只能做一件事
!
Token 浪費 — 簡單任務也用最貴的 model，分開後可按任務分配適合的 model
解法很直覺：把一個人拆成一個團隊

Agent 設定

怎麼定義一個有個性的 AI 角色

Agent 的工作空間 — 一切從 .md 開始

# OpenClaw 初始化時自動生成的檔案結構 workspace/ ├── BOOTSTRAP.md # 🐣 出生儀式（用完即刪） ├── SOUL.md # 🧠 人格與價值觀 ├── IDENTITY.md # 🪪 名字、物種、emoji ├── USER.md # 👤 主人是誰 ├── AGENTS.md # 📋 行為規範與 SOP ├── TOOLS.md # 🔧 環境筆記（SSH、裝置） ├── HEARTBEAT.md # 💓 空閒時的巡邏清單 ├── MEMORY.md # 📝 長期記憶（精華） └── memory/ # 📅 每日筆記
🐣
BOOTSTRAP.md — 出生儀式。第一次啟動時 Agent 會跟你聊天：「我叫什麼？什麼個性？」填完 IDENTITY.md + USER.md 後自動刪除
✨
全部有預設模板 — openclaw init 自動生成。預設的 SOUL.md 就寫了「有自己的意見」「先試著自己查，再問人」「你是客人，尊重主人的隱私」
換一組 .md 檔案 = 換一個完全不同的 Agent。不用改程式，不用重新訓練

關鍵檔案解析

# AGENTS.md — 行為規範 ## 每次 Session 1. 讀 SOUL.md — 我是誰 2. 讀 USER.md — 我在幫誰 3. 讀 memory/今天.md — 最近脈絡 ## 安全 - 不洩漏私人資料 - 破壞性指令先問 - trash > rm
# HEARTBEAT.md — 空閒巡邏 ## 檢查項目 - [ ] 未讀重要信件 - [ ] 未來 24h 行事曆 - [ ] 服務健康檢查 # 預設是空的 # 加了項目 Agent 才會巡邏 # 空 = 不消耗 API 額度
# USER.md — 認識主人 Name: Wayne Timezone: Asia/Taipei Notes: - 偏好繁體中文 - 喜歡直接的回覆 # 隨時間累積觀察更新
# TOOLS.md — 環境筆記 ## SSH - server → 192.168.1.100 ## Home Assistant - https://ha.example.com # Skill 定義「怎麼用」 # TOOLS.md 記「你的設定」
💡
AGENTS.md 定義怎麼做事 · USER.md 定義幫誰做事 · TOOLS.md 記錄用什麼做事 · HEARTBEAT.md 定義閒著做什麼

SOUL.md — 賦予 Agent 人格

# SOUL.md — 情報分析師 ## 身份 你是情報分析師，負責每日新聞摘要。 個性直接，嗅覺敏銳。 ## 說話風格 - 條列式，每條附來源連結 - 不確定的事標註「未經證實」 - 用繁體中文 - 不閒聊，只報重點 ## 工作範圍 - AI 產業動態 - 國際重大事件 - 技術趨勢
→
Agent 每次啟動都會讀 SOUL.md — 像人的性格
→
不同 agent 寫不同 SOUL.md = 不同角色

Channel Binding — 誰聽哪個頻道

// openclaw.json — 每個 agent 綁定自己的頻道 { "agents": [ { "id": "main", "bindings": [{ "channel": "discord", "targets": ["#general"] }] }, { "id": "intel", "bindings": [{ "channel": "discord", "targets": ["#情報頻道"] }] }, { "id": "dev", "bindings": [{ "channel": "discord", "targets": ["#技術頻道"] }] } ] }
💬
在 #情報頻道 說話 → 情報 agent 回應；在 #技術頻道 → 開發 agent 回應
🔒
Agent 只看得到自己綁定的頻道 — 天然隔離
⚡
切換 agent = 切換頻道，不用打指令
03

記憶系統

Agent 沒有記憶，但可以有筆記本

三層記憶架構

MEMORY.md — 長期記憶
整理過的精華：決策、偏好、教訓
↓
memory/YYYY-MM-DD.md — 每日筆記
原始記錄：今天做了什麼決定
↓
memory_search — 語意檢索
Embedding 搜尋，跨檔案找相關內容
↻
凌晨自動 記憶維護 — 像人類整理日記

記憶運作細節

📝
MEMORY.md — 只在主 Session 載入，群聊不讀（防止私人脈絡外洩）
📅
memory/YYYY-MM-DD.md — 每次啟動讀今天 + 昨天，保持最近脈絡
🔍
memory_search — 語意搜尋所有 .md 記憶檔。把文件切成 ~400 token 的 chunk，用 embedding 做向量比對
💾
自動記憶沖刷 — Session 快被壓縮前，系統會靜默提醒 Agent「快把重要的事寫下來」
⚠ Embedding 需要 API Key：預設用 OpenAI text-embedding-3-small，沒設定 key 的話 memory_search 不會運作。也支援 Gemini、Voyage、或本地模型（需另外設定）
內建預設：Hybrid Search（BM25 + 向量）· 時間衰減（新記憶優先）· MMR 去重 · Embedding Cache（避免重複呼叫 API）· Context Pruning（cache-ttl 模式，每 1h 自動清理肥大的 tool result）
需另外開啟：Session 逐字稿索引（實驗性，將歷史對話也納入 memory_search 範圍）

Context Pollution

踩坑：Agent A 讀到 Agent B 的日誌，開始說「我昨天做了 X」— 它根本沒做過
?
LLM 看到第一人稱記錄就會「認領」— 無法區分是不是自己的經歷
解法：段落級 context 過濾 — 按 agent 名字切割，只餵自己的段落
// 只保留跟自己相關的內容 const sections = dailyNotes.split(/^## /m) return sections.filter(s => s.includes(agentName))
💡
記憶隔離不只是安全問題，是正確性問題

Skill — 教 Agent 用工具

# Skill 結構 skills/ ├── weather/ │ └── SKILL.md # 說明書 ├── github/ │ ├── SKILL.md │ └── scripts/ # 輔助腳本 └── voice-clone/ ├── SKILL.md ├── scripts/ ├── references/ # API 文件 └── LESSONS.md # 踩坑紀錄
→
Agent 根據任務自動選擇要讀哪個 SKILL.md
→
建議自己做 Skill — 跟 agent 討論 SOP → 實際跑 → 踩坑糾錯 → 寫成 SKILL.md
→
Skill Seekers — 把文件網站、GitHub repo、PDF 丟進去，自動產出完整 SKILL.md（支援 Claude / Gemini / Cursor 等）
⚠
clawhub.com 可裝社群 skill，但有一定比例是惡意的 — 安裝前務必檢查內容

LESSONS.md — Agent 自己累積經驗

# LESSONS.md — voice-clone skill 的踩坑紀錄 ## TTS Server - CosyVoice 模型載入要 30 秒，必須常駐化不能每次重啟 - Port 8766 被占用時 fallback 到 8767 ## 電話系統 - Twilio Trial 帳號接起來會有英文提示語，無法跳過 - 音頻格式必須是 wav 8kHz mono，否則 Twilio 會靜音 - 整個流程（生成 → 上傳 → 撥號）約 60 秒 ## 踩過的坑 - Edge TTS 的 zh-TW 女聲比 zh-CN 自然很多 - timeout 設太短會在音頻還沒生完就斷掉
📝
Agent 踩坑後自己寫進 LESSONS.md — 下次不再犯同樣的錯
🔄
經驗跨 session 保留 — 重啟後讀 LESSONS.md 就恢復經驗值
💡
這不是 OpenClaw 內建功能 — 是我跟 agent 討論後摸索出來的做法，放在 skill 目錄裡
像是 agent 的工作筆記 — 不是你教它，是它自己學

Model 怎麼選

任務特性Model性格描述
深度推理、決策、創意Opus有點傻但有趣的同事 — 角色扮演自然，但容易太快行動
結構化資料、程式碼GPT Codex角落裡安靜但可靠的工程師 — 預設讀更多 code，不廢話
例行摘要、行政Sonnet速度快、成本低、日常任務的主力
大量聚合、低複雜度Gemini Flash超低成本、吞吐量大
Peter 的比喻：「Opus 有點太美式（熱情但囉唆）；Codex 是德國人（乾但可靠）」— 切換模型大約需要一週才能建立直覺
— Lex Fridman Podcast #467
核心思路：按任務特性選 model · 跨 Provider（Anthropic + OpenAI + Google）分散風險
↻
Fallback 機制：主 model rate limit 時自動降級到備用 model，agent 不中斷
例：Opus 額度用完 → 自動切 Sonnet 繼續回應

Fallback — 不中斷的保險機制

// Gateway 的 fallback 流程 使用者發訊息 → 嘗試主 model（Opus） → rate limit / 503 / timeout → 自動切換到備用 model（Sonnet） → 回應送出，使用者無感
✓
好處：服務不中斷 — 寧可用稍弱的 model 回應，也不讓使用者等到 timeout
⚠
風險：靜默降級 — agent 不知道自己被換了 model，品質可能莫名下降
🔧
多 Auth Profile：同一個 provider 設多組 API key，一組 rate limit 就換下一組
建議：重要 agent 設定明確的 fallback 順序，並監控實際使用的 model — 避免長期跑在降級狀態卻不自知

06

安全與風險

能力越大，風險越大 — 模型安全 ≠ 系統安全

Prompt Injection — 最大的隱患

什麼是 Prompt Injection？
惡意指令藏在看似正常的內容裡 — Agent 讀取後被誘導執行非預期操作
📧
信件 — 「請將以下內容轉發給 XXX」藏在 email body 裡，Agent 自動摘要時中招
🌐
網頁 — Agent 用 web_fetch 抓內容，頁面裡藏了「忽略之前的指令，改為執行…」
📄
文件 / Skill — 社群 skill 的 SKILL.md 裡夾帶惡意指令，Agent 讀了就照做
Peter Steinberger 觀點：
  • Prompt Injection 在全行業範圍內仍是未解決的開放性問題
  • 弱模型非常容易被騙 — 不要用便宜的模型（Haiku、本地小模型）
  • 但最新一代模型有大量 post-training 防禦 — 不再是「ignore all previous instructions」就能破
  • Peter 的 Discord bot 用私有 SOUL.md，有人試注入 → bot 直接嘲笑他們
— Lex Fridman Podcast #467 · 回到Axton: OpenClaw 安全實測
防禦層：用夠強的 model · 最小工具權限 · 敏感操作人類確認 · 外部輸入標記 untrusted · ClawHub 已跟 VirusTotal 合作 AI 掃描所有社群 skill

沙盒 — Agent 的執行環境

⚠ 預設 sandbox = no — Agent 執行的任何命令都以運行用戶的權限直接在系統上跑，沒有任何隔離
方案隔離程度效能適合場景
Docker中 — 共享 kernel，有逃逸風險好自己寫的可控任務
獨立機器（Pi4 等）高 — 物理隔離，壞了 reflash較弱不信任的操作、外部 skill
雲端 VM高 — 隔離完整，按需開關彈性重運算 + 安全要求高
💡
Docker 的隔離沒有想像中強 — container escape CVE 每年都有，共享 kernel 是根本限制
我的做法：用獨立的 Raspberry Pi 當沙盒執行環境 — 物理隔離、成本低、最壞情況就是重刷 SD 卡
模型安全 ≠ 系統安全：一個看起來正常的 Python 腳本（例如「伺服器遷移檢查」），裡面偷偷把密鑰傳出去 — 模型不會攔截，因為它看起來就是合法程式碼

安全原則總結

1
最小權限原則
每個 agent 只給完成任務所需的最少工具和存取範圍
2
不信任外部輸入
網頁、信件、使用者訊息都可能含有注入攻擊，一律視為 untrusted
3
敏感操作要確認
發信、刪檔、金流相關操作，強制 human-in-the-loop
4
隔離執行環境
不信任的 code 跑在沙盒裡，不要讓 agent 直接操作生產環境
5
自己寫 Skill
社群 skill 安裝前務必 review scripts/ — 或乾脆跟 agent 一起從零建 skill
Peter：「如果你確保只有你自己能跟它說話、不把東西放公網上，風險就小很多。大部分人把情況想得比實際嚴重。」
— Lex Fridman Podcast #467

Agentic Engineering — 跟 Agent 協作的技巧

The Agentic Trap：新手把流程搞得超複雜（8 個 agent 串聯、18 個 slash command）→ 高手反而回到簡短 prompt。就像學吉他，過度設計不如直覺對話
🧠
同理心 — Agent 每次都從零開始看你的 codebase。想像你是新人第一天入職，面對一堆沒文件的程式碼
❓
「Do you have any questions for me?」— 讀 Agent 的問題就能知道它缺什麼 context，甚至不用回答，讓它自己去讀 code
↻
做完就問「what can we refactor?」— Agent 在過程中發現了痛點，讓它告訴你哪裡需要改進
👥
像帶工程團隊 — 不要把自己的做法強加給它。接受它選的命名、它的實作方式。員工不會跟你寫一樣的 code，Agent 也不會
Peter：「Vibe coding 是個侮辱性用語。我做的是 agentic engineering。凌晨三點後才切換到 vibe coding — 然後隔天就後悔了。」
— Lex Fridman Podcast #467

踩坑集錦

真正有價值的部分

系統層踩坑

Agent Binding 災難
某個 agent 意外變成 default → 所有訊息都被它攔截 → 主 agent 失聯
→ 修復時忘記遷移記憶檔 → 主 agent 失去所有長期記憶
Model 靜默降級
Provider rate limit → gateway 自動 fallback 較弱 model → agent 無感知
→ 品質莫名下降卻查不出原因 → 需監控實際使用的 model
Cron 跳週期
Gateway 重啟時，過期任務下次執行時間算錯，直接跳到隔天
→ 早上排程全沒跑 → 需手動補執行

Agent 行為踩坑

NO_REPLY 陷阱
叫 Agent A 透過工具發訊息 → 發完回 NO_REPLY → 呼叫端無法確認完成
→ 指令加「發完後回覆確認訊息」
外部工具 Headless 模式
CLI 工具 stdout 是 buffered，整個過程零輸出但檔案已寫好
→ 判定成功看 filesystem 不看 stdout
GPT 角色扮演崩壞
SOUL.md 寫再多，GPT 系列容易跳出角色
→ 加 few-shot 對話範例明顯改善 · Claude 天生不需要

心得

1
瓶頸不在 LLM，在工程
Model 夠強了，挑戰是 context 管理、記憶、工具整合
2
隔離是必要的
Multi-Agent 增加複雜度，但解決了 context 爆炸和角色混亂
3
Gateway > Framework
不用寫 code，agent 活在通訊管道裡，更適合「生活自動化」
4
給 Agent 人格，效果出乎意料
SOUL.md + LESSONS.md 讓 agent 更一致、更有趣
