01

從聊天到做事

AI 不再只是回答問題，而是主動執行任務

什麼是 AI Agent

💬
Chatbot — 你問一句，它答一句 （大部分人對 AI 的認知停在這裡）
🔧
Tool-Use AI — 能呼叫工具：搜尋、寫檔案、查資料庫 （ChatGPT Plugins, Function Calling）
🤖
Agent — 有記憶、有排程、能主動做事、能跟其他 Agent 協作 （這是今天要講的）
關鍵差異：Agent 不需要你每次下指令。它會自己判斷什麼時候該做什麼，就像一個遠端同事。

為什麼要多個 Agent

🧠
專注度 — 一個 Agent 什麼都做，context 會爆。分工後每個 Agent 專注自己的領域
💰
成本控制 — 不同任務用不同模型。簡單的用便宜模型，複雜的用強模型
🔒
權限隔離 — 財務 Agent 看不到客服資料，客服 Agent 碰不到帳務系統
📱
多頻道 — 不同 Agent 綁不同通訊管道（Discord、Telegram、Email）
實務經驗：一個 Agent 試圖處理所有事情時，會把別人的 context 混進自己的回答裡。
分工不只是效率，更是正確性的保障。

中心 Agent 負責跨部門協調，子 Agent 各司其職。任何人的錯不會污染別人的 context。

03

怎麼開始用

從你的工作流程出發，找到適合 AI 的切入點

第一步：盤點你的工作流程

不是「AI 能做什麼」，而是「你每天在重複什麼」。
把日常工作拆成步驟，標記哪些是重複性的、哪些需要判斷。
📝
列出步驟 — 把一個完整任務拆成 Step 1, 2, 3…
🏷️
分類標記 — 每一步是「重複性」還是「需要人類判斷」？
🎯
挑選目標 — 重複性高 + 規則明確的步驟，就是 AI 的切入點
🔗
串接起來 — 把多個自動化步驟串成一條完整流程
步驟內容性質AI？
1收到新資訊（信件 / 公告）被動接收✅ 自動監控
2整理摘要、擷取重點重複性✅ 結構化輸出
3判斷優先順序 / 決策需要判斷👤 人類
4執行動作（回信 / 建檔）重複性✅ 自動執行
5追蹤進度、定期回報重複性✅ 排程巡檢

第二步：把流程變成 Skill

什麼是 Skill？

📄
一份 SKILL.md 說明文件
📜
搭配的 腳本（API 呼叫、資料處理）
📚
參考資料（格式範例、規則）
Skill 就像一份 SOP 文件——
告訴 Agent「遇到這種任務時，照這個流程做」。

範例結構

# 每日情報摘要 Skill ## 觸發條件 每天 07:30 自動執行 ## 步驟 1. 用 web_search 搜尋關鍵字 2. 用 web_fetch 抓取內容 3. 結構化整理成摘要 4. 發送到指定頻道 ## 輸出格式 🔹 **類別**：標題 + 一句摘要 連結：原始 URL ## 注意事項 - 每條必須附原始連結 - 不要預覽連結內容

第三步：跑一次、改一次、越來越準

📝 寫 Skill
第一版不用完美
→
▶️ 讓 Agent 跑
觀察實際行為
→
👀 看哪裡不對
輸出格式？遺漏？
→
✏️ 修改 Skill
補規則、加範例
LESSONS.md — Agent 自己會把踩過的坑記下來。
下次執行同樣的 Skill 時，會自動參考之前的教訓。

不是你在訓練 AI，是 AI 在累積自己的工作經驗。
💡
實務上大概 3-5 次迭代，一個 Skill 就能穩定運作。之後就是全自動。

Skill 的生命週期 — 多 Agent 協作強化

🧝‍♀️ 主 Agent
撰寫第一版 Skill
→
🤖 執行 Agent
實際跑任務
→
📝 踩坑
寫入 LESSONS.md
→
🔄 下次更好
自動參考教訓
🧝‍♀️ 主 Agent（Opus）
理解意圖、設計流程、撰寫 Skill 初版。
擅長全局規劃和複雜推理。
寫完交給專責 Agent 去跑。
🤖 執行 Agent（Sonnet / GPT）
照著 Skill 重複執行。速度快、成本低。
遇到邊界案例就記進 LESSONS.md。
累積的經驗讓 Skill 越來越穩。
Model 互補：強模型負責「設計」，輕模型負責「執行 + 學習」。
Skill + LESSONS.md 讓便宜模型也能做出強模型品質的工作——因為經驗都寫在檔案裡。

架構遷移 + 建置心得

同樣的模式放到不同場景，加上實戰中學到的事

架構是通用的，換的是 Domain Knowledge

核心能力就這幾個：情報監控、排程執行、異常偵測、跨系統串接、主動通知。
放到不同產業，只是換監控對象和觸發條件。
🏦
金融
法規變更追蹤
交易異常偵測
財報自動摘要
客服分流
🏥
醫療
病歷摘要
排班管理
藥物交互作用檢查
檢驗報告追蹤
🏭
製造
供應鏈監控
設備異常預警
品質檢測報告
庫存管理
🔑 共通模式
情報 Agent = 監控特定來源 → 結構化摘要
風控 Agent = 偵測異常 → 評估 → 通知
助理 Agent = 排程 → 執行 → 回報
⚠️ 關鍵差異
安全等級不同（金融 > 個人）
合規要求不同（需要稽核日誌）
Human-in-the-loop 的粒度不同

記憶系統 — Agent 不是金魚

三層記憶

📝
Daily Notes — 每天的原始記錄
🧠
長期記憶 — 提煉後的精華
📚
共享知識庫 — 跨 Agent 經驗

運作方式

📖
每次啟動先讀最近記憶
✍️
重要事件即時記錄
🔄
定期回顧 + 提煉精華
Agent 每次 session 重啟都會失憶。記憶系統就是它的延續性——
就像人類靠筆記本記住重要的事，Agent 靠 .md 檔案。

模型策略 — 不是最貴的就最好

任務類型推薦模型原因
核心決策 / 創意Opus需要深度推理和角色一致性
日常任務 / 排程Sonnet速度快、成本低、能力足夠
大量文件處理GPT-5.3 Codex長 context、結構化輸出穩定
情報掃描Gemini Flash超便宜、速度極快
Fallback 機制很重要 — 某個模型 API 掛掉時，自動切換到備援模型。
Agent 系統最怕的不是回答不好，是完全沒回應。

安全 — 最重要但最容易忽略

💉
Prompt Injection — 最大隱患。使用者輸入可能竄改 Agent 行為
🔐
權限隔離 — 每個 Agent 只能存取需要的資源，最小權限原則
📝
稽核日誌 — 所有 Agent 行為都要可追蹤、可回溯
🧪
沙盒執行 — 程式碼在隔離環境中運行，不影響主系統
👤
人類把關 — 破壞性操作（刪除、發送、金錢）一律需要確認
金融場景對安全的要求更高：Agent 可以建議，但不能直接執行交易。
Human-in-the-loop 不是退步，是負責任的設計。

踩過的坑

🧠 Context Pollution
Agent 讀到別人的記憶，把其他 Agent 的經歷當成自己的。
→ 記憶需按 Agent 過濾
🤖 角色漂移
GPT 系列模型容易忘記人格設定，講到一半變成通用助手。
→ 需要 few-shot 範例固定風格
⏰ 排程失靈
系統重啟後，排程器計算下次執行時間出錯，跳過整天。
→ 需要 fallback + 手動補執行機制
🔇 靜默失敗
Agent 執行完工具但不回報結果，以為自己已經回覆了。
→ 指令中明確要求「做完要回報」
最大的教訓：Agent 不會主動告訴你它搞砸了。需要主動設計監控和驗證機制。

與 Agent 協作的技巧

📐
結構化指令 — 明確的輸入 / 輸出格式，減少歧義
🔄
迭代改進 — 不要期待一次到位，觀察行為後調整設定
📝
經驗累積 — 讓 Agent 把踩過的坑記下來（LESSONS.md）
🎯
關注意圖 — 先理解需求再動手，「你有什麼問題想問我嗎？」
🧪
自我反省 — Agent 遇到問題時，讓它去讀自己的 source code 理解原因
Agentic Engineering 不是寫更好的 prompt。
是設計一個讓 Agent 能持續學習和改進的系統。

總結

01
AI Agent ≠ Chatbot — 它是有記憶、有排程、能主動做事的數位同事
02
Multi-Agent 分工 — 每個 Agent 專注一件事，比一個全能 Agent 更可靠
03
架構可遷移 — 電商、金融、任何需要多角色協作的場景都適用
04
安全第一 — Human-in-the-loop + 權限隔離 + 稽核日誌
05
持續演化 — Agent 會學習、會記住、會變得更好。但需要你設計好演化的機制
